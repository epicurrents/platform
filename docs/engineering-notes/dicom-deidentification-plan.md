# DICOM de-identification on ingest — plan

Decided 2026-11-21. The dicom plugin stores and serves uploaded files unchanged today, so every grantee, every reader of an attached recording and every DICOMweb client receives the patient's identifying tags. This plan makes de-identification at ingest the default, the way the recording pipeline already works: the stored file is clean, so every serving surface is clean without knowing about it. Tool choice is in [dicom-deidentification-tools.md](dicom-deidentification-tools.md); the work it builds on is in [plugins/dicom/README.md](../../plugins/dicom/README.md).

The output is pseudonymised personal data, never anonymous. No string, notice or document may call it otherwise ([docs/anonymisation-compliance.md](../anonymisation-compliance.md)).

## Decisions

| # | Question | Decision |
|---|---|---|
| 1 | Default | On: `DICOM_DEIDENTIFY_ON_INGEST`, default `True`. No deployment has run the plugin, so no mixed archive results. Off is an operator's deliberate choice and keeps today's behaviour |
| 2 | Dates | Dummied, as the basic profile does and as the recording pass does with its fixed start date |
| 3 | Patient sex and age | Blanked by default; a retain option `DICOM_RETAIN_PATIENT_CHARACTERISTICS` (default `False`) maps to Annex E's Retain Patient Characteristics option |
| 4 | Study and series descriptions | Kept (override the profile's action to K), and run through `epicurrents.text_hygiene.name_warnings`, whose rows the upload response returns, as every grantee-visible label write does |
| 5 | Private tags | Deleted wholesale; a safe-private allowlist waits for a modality that needs one (MR diffusion b-values are the likely first) |
| 6 | Burned-in pixel text | **Author confirmation, not refusal.** Ultrasound is a main use case (combined NCS + US), so it cannot be refused. See [Burned-in text](#burned-in-text) |
| 7 | Originals | Kept in the write-only originals volume the recordings use, under its no-read-back rule |

## Design

### The pass

A new module `plugins/dicom/deidentify.py` holding `deidentify_dataset(ds) -> Dataset`, built on Kitware `dicom-anonymizer` (2.1.0 at the time of writing, BSD-3-Clause, depends on pydicom and tqdm only). Add it to the platform requirements via `scripts/lock-requirements.sh` — a plugin's dependency goes in its own requirements file if it has one; check how the dicom plugin declares pydicom first. Re-verify the Annex E table edition the 2.1 release ships before relying on the note's 2023e claim.

- **UIDs.** Every U-coded tag goes through an override producing `2.25.<decimal of 128 bits of HMAC-SHA256(key, original UID)>` (PS3.5 B.2), the RSNA CTP `@hashuid` idea. Deterministic across requests, workers and restarts, so a study uploaded in several batches converges on one row and per-author dedup keeps working. The key is a new dedicated secret `DICOM_UID_KEY` generated by `init_env`, not `SECRET_KEY`, so rotating the session secret does not shatter every study. A release that needs it declares it in an `env-additions` file (plugin-level, `plugins/dicom/env-additions`), per [scripts/updater/README.md](../../scripts/updater/README.md#settings-a-release-introduces); the setting has no value every deployment can share, so its absence must degrade to refusing de-identified upload with a clear message rather than failing boot.
- **Dummy values.** The library's person-name dummy must not read "ANONYMOUS" or anything like it, since it is displayed in the study list and OHIF — override PN dummies to the recording pass's `X` convention. Check every dummy the library writes for the same reason.
- **Marking.** Write `PatientIdentityRemoved=YES` and `DeidentificationMethod` (naming the pass version), and the Annex E option codes in `DeidentificationMethodCodeSequence`.
- **Versioning.** A constant `DICOM_DEIDENTIFICATION_VERSION`, stamped per study (`DicomStudy.deidentification_version`, plus whether patient characteristics were retained), with a test pinning a digest of the pass's source to the constant, exactly as [recordings/tests/test_deidentification_record.py](../../recordings/tests/test_deidentification_record.py) does for the recording pass, so a behaviour change without a bump fails the suite.
- **Load-bearing.** `deidentify.py` gets a `⚠️ LOAD-BEARING` docstring block and a row in the AGENTS.md registry with its contract test. That is a rule change to AGENTS.md, made in the same commit.

### Ingest

In [plugins/dicom/ingest.py](../../plugins/dicom/ingest.py), shared by the upload endpoint and `index_dicom`:

1. Parse the header as today (`stop_before_pixels=True`) to decide the burned-in question before reading pixels.
2. When de-identification is on: read the staged file in full, write the original to the originals volume, run the pass, `save_as` back to the staged path, recompute `file_size` and `file_hash` from the rewritten bytes.
3. Extract fields from the cleaned dataset, so the model's `patient_*`, `study_*` and `accession_number` fields hold the cleaned values with no extraction change.
4. Persist and move as today.

`write_original` in [recordings/preservation.py](../../recordings/preservation.py) takes a `Recording`; give DICOM a sibling or generalise it to an object plus a label, keeping its never-read-back contract and the `validate_originals` metadata-only checks.

`index_dicom --resume` matches on a file's content hash, which after rewriting is the cleaned file's. Store the source digest on the instance as `source_hash` for resume detection, and treat it as `Recording.file_hash` is treated: a bit-exact link to the original, never serialised to anyone, the author included, and registered as masked in the audit trail.

The stored file being clean makes the attachment-inheritance gap recorded in the ROADMAP moot while the setting is on. With it off, apply the narrow fix: `can_read_via_attachment` conveys nothing when the parent grant de-identifies.

### Burned-in text

Header cleaning does not touch text rendered into the pixels. Until a redaction stage exists, the author attests instead:

- **Which files.** Modality `US`, `SC` or `OT`, or `BurnedInAnnotation=YES` on any modality. Decided from the parsed header on the server; the browser is never the authority.
- **The flow.** An upload without the confirmation refuses those files per file with an error code (for example `burned_in_confirmation_required`) and writes nothing for them — the staged file is deleted, as for any rejected file — while accepting the rest of the batch. The Upload dialog in [DicomStudiesView.vue](../../frontend/src/plugins/dicom/DicomStudiesView.vue) then shows how many images need checking and a checkbox ("I have checked these images and they show no names, IDs, dates or other identifying text"), and resubmits only those files with `confirm_burned_in=true`. `index_dicom` gets a `--confirm-burned-in` flag with the same meaning.
- **The record.** The confirmation is recorded as booleans and counts in the upload's Activity metadata, never as text, and on the instance as a field saying the pixels were attested rather than checked (for example `pixel_review = attested | not_required`), so a later redaction stage or a re-review can find them. The actor is the Activity row's user; no new user foreign key, so no new erasure or export registration.
- **Honesty.** README, the dialog and the assessment say the attested images were checked by the uploader, not by the platform. A later optional Celery stage running `presidio-image-redactor` on the same modalities can replace or supplement the attestation; out of scope here.

### Surfaces that change for free

Study list, study detail, OHIF JSON, DICOMweb, WADO-URI, sharing and attachment inheritance all read the stored rows and files, so none of them needs a change. The Share dialog's notice ("served as uploaded … not de-identified") becomes conditional on the setting and on the study's `deidentification_version`.

## Phases

1. **Pass and ingest.** `deidentify.py`, the UID key setting and `init_env` support, the rewrite in ingest, `source_hash`, originals volume, version stamp, migrations. Tests: every Annex E action class on a fixture dataset, UID determinism across two calls and two keys, a split-batch upload converging on one study, extracted fields holding cleaned values, `file_hash` of the rewritten file, `source_hash` never serialised, resume matching on the source digest, the digest-pin test, setting off leaves bytes unchanged.
2. **Burned-in attestation.** Server refusal and confirmation, `index_dicom` flag, `pixel_review` field, Upload dialog flow, Activity metadata. Tests: each trigger (US, SC, OT, flag on CT), mixed batch partly accepted, confirmed resubmission accepted, nothing written for a refused file, no text in metadata.
3. **Descriptions and notices.** `name_warnings` on descriptions in the upload response, the conditional Share notice, the attachment fix for the off case.
4. **Documentation and review.** Plugin README (a De-identification section replacing the 🔴 roadmap item), the tool note's integration sketch marked superseded by this plan, the external plugin docs, `.env.example` only if the key needs a placeholder, ROADMAP, the assessment's DICOM given-data row and a dated log row (classification: pseudonymised, no longer raw), AGENTS.md load-bearing row. Run the handover checklist: `phi-exposure`, `gdpr-compliance`, `anonymisation`, `audit-trail-completeness`, `csrf-coverage`, `load-bearing-diff-reviewer`, `documentation-style`.
5. **End to end.** Rebuild the dev stack, re-import the test studies plus an ultrasound sample, check in Chrome that OHIF shows the dummies, that the study and series hierarchy survives, that an US upload asks for the confirmation, and that the platform test studies still render.
